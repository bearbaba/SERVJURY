## Direct OpenServ capability result from Task 750592 (operator evidence)

The expanded **`Tool call: adjudicate_delivery`** returned:

```json
{"status":"NOT_VERIFIED","reason":"GenLayer transaction outcome uncertain; inspect chain before retry"}
```

This message is generated by `agent/openserv-agent.mjs` **only when the caught GenLayer error carries `error.txHash`**. The active `src/genlayer.mjs` code assigned this hash after submitting a `file_case` or `adjudicate_case` transaction, if its subsequent confirmation failed. Crucially, the original `confirmFinalizedWrite()` used a read-only `getTransaction` fallback **only if** `waitForTransactionReceipt()` returned an incomplete receipt; if that function threw, the fallback was skipped. This explains **a plausible code-level path** for a successfully persisted `file_case` to be reported as uncertain. It does not prove the exact exception occurred, or whether an adjudication write was submitted.

At the Nov 10 public contract-history audit (10 total transactions), only this case-matching transaction was present:

- `file_case` **`0x66de388fd40a96bbd07d625befacfda98a002907a5656f5075e6e781c88274c6`**: `FINALIZED`, two GenVM leader receipts `SUCCESS/SUCCESS`.
- No matching `adjudicate_case` observed in this limited history.
- Contract remained `FILED`. The terminal `Done` OpenServ task output cannot substitute for an on-chain verdict.

**Preventative fix**: `confirmFinalizedWrite()` now uses read-only `getTransaction({hash: originalHash})` even when the initial waiter throws, and accepts success only for stored `FINALIZED` plus unambiguous GenVM success. If that query also fails or remains pending/ambiguous, the function fails closed and preserves the same transaction hash. It does **not** sign/retry another transaction, does **not** retroactively repair Task 750592 and does **not** prove the error was a waiter timeout.
